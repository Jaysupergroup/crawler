CrawlLoom / App review

Efficiency, reliability, and security findings.

A broader review of the crawler, dashboard, API, storage, and deployment model. The findings below describe observed behavior, its impact, and the work that would make the application more dependable at larger scale.

How the app currently works

The Express server authenticates users, creates dashboard sessions, starts SiteCrawler instances, streams progress over Server-Sent Events, coordinates optional MySQL persistence, and generates exports. The React dashboard consumes those APIs, while the engine handles browser navigation, direct HTTP extraction, SEO data, resources, and link checks.

This architecture is effective for a single server, but the server process currently owns too much state and too many long-running responsibilities. That is the central theme of this review.

Primary finding: crawl work is coupled to the API process

When a crawl starts, server.js creates and runs the crawler directly while also serving authentication, dashboard requests, SSE connections, history, and exports. The server limits concurrency, but busy browser work still competes with ordinary API traffic for process resources.

Impact: several large crawls can increase memory pressure and make status updates or exports feel slow. A restart also loses active in-memory crawler state.

Direction: represent each crawl as a durable job, process jobs through a fixed worker pool, and expose explicit queued, running, completed, and failed states.

Finding: large audits cost memory in the browser

The dashboard receives and retains complete page and link collections for the active audit. Pagination reduces the number of visible rows, but it does not reduce the memory required for the full audit.

Impact: multi-thousand-page crawls can make rendering, filtering, issue analysis, and history restoration expensive.

Direction: virtualize large tables, load history with cursors or pages, and move expensive SEO analysis into incremental processing or a Web Worker.

Finding: persistence is page-by-page and failure visibility is limited

Each crawled page is queued for a database write. Persistence errors are logged while the crawl continues, so the in-memory audit can finish even when the saved history is incomplete.

Impact: users may believe a completed historical crawl is complete when some pages or links were never stored. Individual database operations also add avoidable round trips.

Direction: batch page and link writes, track persistence status separately, and show a clear warning when saved history is incomplete.

Security and correctness findings

Subdomain matching: a suffix-only hostname check can treat an unrelated hostname as a subdomain. Require an exact host match or a hostname beginning with .root-domain.

Redirect enforcement: cross-domain redirects are detected and logged, but the crawler must abort or reject the navigation when blockCrossDomainRedirects is enabled.

Page limits: concurrent workers can all pass a limit check before the shared counter is updated. Reserve capacity when a URL enters processing so the configured maximum is exact.

DNS consistency: hostname validation and the later browser or HTTP connection resolve independently. A controlled proxy or pinned connection path would reduce DNS-rebinding risk.

Operational and maintenance findings

Active crawls, dashboard sessions, and SSE clients are stored in process memory. This is acceptable for one instance, but it prevents reliable restart recovery and horizontal scaling. Shared session and job storage should come before multi-instance deployment.

The legacy dashboard remains available beside the supported React dashboard and is not maintained in lockstep. That creates duplicated behavior and security assumptions. It should be formally isolated, tested as a compatibility surface, or retired.

Large Excel exports should run as background jobs, browser instances should be reused through a controlled pool, and versioned public assets should use long-lived cache headers.

Recommended implementation order

  1. Fix hostname boundaries, redirect enforcement, and exact page-limit accounting.
  2. Introduce the durable crawl queue and worker pool.
  3. Batch persistence and report incomplete saved history.
  4. Virtualize tables and paginate large history restores.
  5. Move exports and heavy issue analysis out of the main request and render paths.
  6. Choose a retirement or compatibility plan for the legacy dashboard.
