CrawlLoom / Efficiency

Queue the crawl work.

The highest-impact efficiency improvement is a central crawl job queue backed by a fixed worker pool.

Why this matters

At present, the server starts crawler work directly from the API process. Several crawls can compete for CPU, memory, and browser resources at the same time, which can make both crawling and the dashboard less responsive.

Recommended change

  • Create a queued job when a user starts a crawl.
  • Run only as many jobs as the server can support through a fixed worker pool.
  • Report clear queued, running, completed, and failed states.
  • Persist jobs so queued or completed work is not lost during a server restart.
  • Run crawl workers separately from the API process so the dashboard remains responsive.

Expected result

The existing MAX_CONCURRENT_CRAWLS limit can become the worker-pool limit instead of rejecting work when all slots are occupied. This smooths out load, reduces memory spikes, and gives users predictable progress while keeping the API available.
